# Network journal implementation details

Companion to [the review plan](../PLAN-NETWORK-JOURNAL.md). The design uses one application journal for both Kist replication and item awards. It does not use a separate delivery protocol. Character saving is independent of journal acknowledgment.

Implementation evidence and remaining integration gates are recorded in the
[M1 work log](network-journal-m1.md), [M2 work log](network-journal-m2.md), and
[M3 work log](network-journal-m3.md). M3 implements SQLite storage/recovery and
the atomic migration pipeline with process-termination evidence. The
[M4 work log](network-journal-m4.md) records replication/session verification;
[M5](network-journal-m5.md) completes adapter foundations and Windows game probes,
including the real legacy decoder. [M6](network-journal-m6.md) now owns live
integration and platform gates; game validation and release move to M7.

## Terminology

A hird is a player group; its Kist/vault is the shared inventory. The anchor is its world location for range checks. Deposits move items into it; takes move items out. The roster is the invite list of eligible connected players, not current membership. Stations are game objects that consume materials, such as smelters. A prefab is an item template. World-level filtering is the game's exclusion of older items from stock queries; Kist stock deliberately bypasses it. A listen host runs a server and local character together; a dedicated server has no local character. Harmony intercepts game methods.

### Standard terminology audit

This is a single-authority replication protocol. Its application-specific terms and policies are defined below; they are not claims of consensus, a distributed database transaction, or exactly-once character persistence.

| Term used | Standard meaning and use here |
| --- | --- |
| Checkpoint state | Saved application state at sequence C. Replaces “committed Kist,” which incorrectly suggested later entries were not yet committed to the database. |
| Replication log / journal | Ordered application records sent to clients. Retained entries follow checkpoint C through log head H. This is distinct from SQLite's page-level WAL. |
| Current state / materialized view | State obtained by applying retained log entries to the checkpoint. New commands validate against this state. |
| Database commit | Successful completion of a SQLite transaction storing state and log entries atomically. Happens before publication and does not wait for client acknowledgment. |
| Application checkpoint / snapshot | Serialized state at a specific application sequence. Checkpoint identifies the retained replay baseline; snapshot also describes its transferred representation. |
| Checkpoint advancement / log truncation | Fold an acknowledged prefix into checkpoint state and delete that prefix. This is prefix truncation, not per-key log compaction, historical rollback, or SQLite WAL checkpointing. |
| Request / command | Client intent, such as taking an item. A log entry records the result selected by the server, not a command clients independently revalidate. |
| Request ID / idempotency key | Client-generated retry identity. Reusing it with the same payload returns the same recorded result; changed payload is rejected. |
| Operation ID | Server identity of an application operation. Replaces the ambiguous “transaction ID”; an operation's lifecycle involves multiple SQLite transactions. |
| Sequence number / log position | Ordered entry number within a vault/epoch. Determines replay order, not operation identity. One operation can be referenced by both its original entry and a later compensation. |
| Processing acknowledgment / cumulative acknowledgment | Confirms verified application through a consecutive sequence, including the recipient's item delivery or depositor's local removal. Confirms neither mere packet receipt nor a character save. |
| Minimum acknowledged sequence | Minimum position among checkpoint participants (active, logging-in, and logging-out sessions), used as our checkpoint cutoff. A new login initially holds C as a retention floor rather than a verified acknowledgment. This all-participant rule is an application policy, not a quorum commit or consensus commit index. |
| Item delivery / award | Addition to the recipient's in-memory character inventory. “Award” is existing game-domain wording for this delivery, not another transaction protocol. |
| Compensating entry / cancellation | A new operation returns items without erasing the original entry. “Canceled” means stop attempting the original character delivery and compensate its server debit; it does not undo items already added to a character. |
| Kist suspension / Kist ban | Application-specific, temporary denial of Kist access. “Self-ban” means the client requests its own suspension. Neither term means server disconnection or a Valheim account ban. |
| Kist login / session / active client set | Application subscription and verified catch-up, followed by access permission. Session identity rejects stale traffic. The checkpoint participant set includes logging-in and logging-out sessions as well as active sessions; the active set determines mutation access. |
| No-op heartbeat | A sequenced entry with no inventory delta, used to exercise checksum verification and acknowledgments during idle periods. Timeout suspects an unhealthy session; it does not prove the peer is offline. |
| Checksum / canonical encoding | A deterministic hash of identically encoded Kist records. Use SHA-256 initially; specify ordering and binary representation. Detects divergence, not authenticity or honest client execution. |
| Epoch / deduplication / tombstone | Epoch separates incompatible histories after restore; deduplication suppresses repeated requests/deliveries; a tombstone retains enough identity/status to reject a forgotten retry. |
| Group commit / backpressure | Multiple ordered database changes share a commit/flush; admission or sending is slowed when queues grow. Neither permits publishing before a successful database commit. |

The snapshot-and-replay terminology follows the [Azure event-sourcing discussion of snapshots and projections](https://learn.microsoft.com/en-us/azure/architecture/patterns/event-sourcing). This design prunes covered history and does not promise a permanent event-sourcing audit log. The shared state/message transaction follows the [transactional outbox pattern](https://microservices.io/patterns/data/transactional-outbox.html); no extra outbox table is required because the replication log serves that role.

[SQLite's WAL documentation](https://www.sqlite.org/wal.html) distinguishes committing a database transaction from checkpointing WAL pages. Our checkpoint-participant policy is an additional application rule. [SQLite transaction semantics](https://www.sqlite.org/lang_transaction.html) apply only inside the server database; there is no transaction held open across client RPCs.

[Consumer acknowledgment documentation](https://www.rabbitmq.com/docs/confirms) supports the distinction between processing acknowledgment and producer-side confirmation, including cumulative acknowledgment. Our acknowledgment means in-memory processing, not a durable character save. Retry deduplication supplies idempotent request effects in the sense of [RFC 9110's idempotency definition](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2); a withdrawal is not inherently idempotent without its request key.

The return path follows the [compensating transaction pattern](https://learn.microsoft.com/en-us/azure/architecture/patterns/compensating-transaction): append a corrective action while preserving concurrent work. It is not a rollback to an old inventory. The periodic no-op serves a [heartbeat/failure-detection purpose](https://www.rabbitmq.com/docs/heartbeats), but our 10-second entries and 30-second timeouts are specific policy choices. End-to-end delivery is neither exactly-once nor guaranteed at-least-once persistence: cancellation and independent character saves intentionally allow duplication and loss in documented cases.

## SQLite schema and server ordering

Use tables for vaults, item stacks, journal entries, request results, operation status/deadlines, persisted session lifecycle and checkpoint participation, and per-client acknowledgment counters. SQLite handles WAL, checkpoints, and disk recovery. The application journal is an ordinary table, not SQLite's WAL. Use a single writer and initially WAL mode with synchronous FULL; verify provider/native-library compatibility and benchmark commits off the Unity game thread. Group commits can share disk flushes. Stage dependent changes in order; only publish committed results.

Maintain three explicit states: checkpoint state at C, replication log entries C+1 through H, and materialized current state at H. Current state is the checkpoint plus replay of the log, including overflow and other checksummed state. Store the checkpoint separately from current item rows; update current rows and append entries in the same SQLite transaction. At startup, reconstruct current state from checkpoint plus log and verify it against persisted current rows before serving requests. Database commit precedes publication; checkpoint participant positions control application checkpoint advancement only.

A vault has world ID, hird ID, and history ID (epoch). Change epoch after restoring older history. Stack IDs remain stable and are never reused within an epoch. Client request IDs are unique and held in memory only; the server maps each to one operation ID and checks payload equality on retries. Do not create a new operation when retrying an uncertain request. Retain request tombstones or an explicit rejection policy after pruning results so forgotten retries cannot become new withdrawals.

Sequence numbers order journal entries within a vault/epoch. They differ from operation IDs: a timeout return has a new sequence number and references the original operation. Store journal entry, per-item changes/effect identities, request result, and operation status in the same database transaction. Persist acknowledgment deadlines when committed entries are first queued for asynchronous delivery. Definitive operation rejections also receive a sequence number and unchanged-state checksum. Admission error `TRANSACTION_DEPTH_EXCEEDED` is transient, allocates no sequence, and does not consume the request ID; retry the same request and payload after at least 100 ms without blocking the game thread. Read current state and validate under the single-writer order; never let two requests spend the same last item.

An entry contains sequence number, operation ID, request/actor identity, operation type, exact changed records/deletions, resulting checksum, and any character delivery with recipient and item payload. Return entries identify the operation being compensated. Keep membership and permission checks server-side; authenticate transport sender and verify server provenance on clients. Clients only receive their hird's permitted history and their own delivery payloads as appropriate.

## UUID sessions and transaction admission

Each item transaction applies to only one stack and carries one character effect for an exact quantity. A multi-stack action, including crafting or a deposit spanning destination stacks, uses separate item transactions, each with its own request ID, operation ID, journal sequence, and effect identity. Split quantities at stack boundaries before admission. SQLite commits and lifecycle settlement may atomically group multiple entries while preserving those separate item transactions. Compensation likewise uses separate single-stack entries if a return requires multiple stack changes.

Each accepted login gets a server-generated session UUID bound to authenticated player, vault, and epoch. Bind all mutations, journal deliveries, acknowledgments, and logout to it. Under writer ordering, permit at most one logging-in, active, or logging-out session per player/vault. Retrying the same login request returns its UUID and Login marker; a different login request while a session exists returns `SESSION_EXISTS`. Closed UUIDs never become valid again. Server restart invalidates old sessions and settles pending operations before new logins.

Use a configurable maximum transaction depth for admitted mutations queued for or executing in the writer, including committed item transactions awaiting the initiating client's processing acknowledgment. Check deduplication before admission; retries of admitted requests consume no additional slot. Check depth and reserve a slot atomically. When full, respond `TRANSACTION_DEPTH_EXCEEDED` without admitting work, mutating stock, allocating a sequence, or recording a terminal request result. The client schedules a retry of the same identity/payload after at least 100 ms; each repeated depth error repeats the delay. Database commit alone does not release an item transaction's slot. Release it exactly once with persisted processing acknowledgment, recorded definitive rejection/failure, or committed exclusion settlement completing the deposit or compensating the withdrawal. Mutations with no character effect release depth on commit or definitive failure. Observer acknowledgments affect checkpoint retention separately and do not retain a completed item transaction's slot. Acknowledgments, heartbeats, lifecycle cleanup, and compensation bypass mutation admission so they can release slots even at the limit. Recover pending depth from durable operation status after restart and settle invalidated sessions before admitting new work. Backoff does not extend any existing deadline or impose a Kist ban.

## Asynchronous execution

Only initiating request validation/admission may be synchronous. Cross-client changes use committed journal entries and asynchronous sequence acknowledgments exclusively; no synchronous broadcast or all-client acknowledgment barrier is permitted. The single writer serializes database work outside the Unity game thread. Perform encoding, checksum calculation, snapshot/checkpoint work, and network fan-out outside that thread as well, using immutable records. Unity inventory/UI calls use bounded game-thread batches that yield between batches. No update loop drains an unbounded queue or rebuilds all clients' state. Slow-client sending and processing cannot block healthy clients' admitted work or acknowledgments; new work remains subject to the pending-transaction limit. Checkpoint retention never becomes a synchronous gameplay barrier.

Assume reliable, ordered RPC delivery within each live connection. M5 records the installed-game transport audit and TCP loopback evidence; using ZRoutedRpc does not itself establish TCP or authenticate its claimed sender field. M6 connects authenticated direct RPCs; M7 confirms each supported transport during network disruption and reconnect on dedicated servers and listen hosts. Application recovery handles connection loss and uncertain outcomes across reconnects. Add retransmission or gap recovery only if validation shows the transport needs it. Library loss/reordering fault injection is defensive testing, not a claim that the live transport exposes individual lost packets or reordered RPCs.

## Client processing and acknowledgment

Apply entries in order to temporary replica state. Verify the checksum before installing changes or adding character items. If valid, install the Kist update and apply the award only on its recipient's client. Every single-stack item transaction has one journal effect identity and exact quantity. Remember applied effect IDs in memory to suppress duplicates; a multi-stack action consists of separate transactions and never retries completed transactions as a batch. Acknowledge the highest consecutive fully processed sequence; repeat acknowledgments for duplicate entries. Full character inventory leaves an award unapplied and its entry unacknowledged until it can fit or is canceled.

The server persists acknowledgment counters and continues accepting independent requests while waiting for them. Active sessions and protected logging-in/logging-out sessions belong to a vault's checkpoint participant group. Only active sessions may submit mutations. Track the requesting player's acknowledgment separately from observers; only its processing confirms its award. Bind acknowledgments to authenticated player, vault, epoch, Kist session ID, and sequence. Reject sequences not sent or covered by an explicitly verified snapshot. An acknowledgment counter cannot skip an unapplied award or pending local deposit removal; snapshots preserve the server settlement outcome of excluded sessions; settled deposits and canceled withdrawals do not require old character effects to be replayed.

A client's replica, last verified sequence/checksum, and applied character-effect set are ephemeral. Use the [login, deposit, and logout sequences and diagrams](../PLAN-NETWORK-JOURNAL.md#login-sequence). Login captures checkpoint C, appends Login L, and registers a logging-in checkpoint participant at C in one writer transaction. Retain the immutable snapshot and every subsequent entry, not just C+1 through L. The initial C is retention protection, not a verified acknowledgment. Verify catch-up through L before enabling mutations; activate the same participant without removing its checkpoint protection. Subsequent entries remain covered by its position. Login retries reuse the marker and cannot extend its 30-second completion deadline. Mismatch/timeout invalidates the session and releases protection through suspension/cleanup. No client protocol state is persisted: request IDs, reservations, replica progress, and per-item effect IDs are memory-only. No per-award completion file or character-save callback is used. Acknowledgment confirms in-memory materialization only; character-save loss is accepted.

Append a NoOp heartbeat entry every 10 seconds per vault with active clients, independently of inventory activity. Use the same database writer, sequence allocation, replication, verification, and acknowledgment code as other entries. The entry has no stack changes or character delivery and carries the checksum of the immediately preceding current state at the log head, not an older checkpoint. Advance the sequence despite unchanged content. Each active client must acknowledge it; sending or receiving it does not reset an outstanding acknowledgment deadline. With no active clients, skip generation and resume the interval when a client becomes active; do not accumulate missed ticks during downtime. Use a server monotonic timer, not client time.

No-op acknowledgment failure invokes the same suspension, pending-item returns, checkpoint-group removal, and 30-second cooldown as any other entry. If no earlier entry is outstanding, a client that stops responding just after a tick is detected approximately 40 seconds later: up to 10 seconds until the next no-op plus the 30-second acknowledgment timeout. A no-op checksum mismatch immediately requests self-ban, just like any other checksum mismatch; it must not be acknowledged merely because it changes no items.

## Kist bans, returns, and application checkpoints

When a journal entry is first queued for asynchronous delivery to an active client, start a 30-second acknowledgment deadline. Track the oldest queued but unacknowledged entry; repeated sends, unrelated requests, and attempted reconnects do not extend it. Persist recovery state and UTC expiry times across server restart; use monotonic timers while running. If no acknowledgment arrives in time, suspend that client's Kist session for 30 seconds. This is not a Valheim kick or server ban: the game connection remains open and the player may continue non-Kist gameplay.

A checksum-mismatch report invokes this same suspension handler immediately, without waiting for the acknowledgment deadline. Authenticate the request against the reporting player's current Kist session; it can suspend only that player, including a session still logging in. Make duplicate reports idempotent so retransmission cannot return awards twice or extend an existing cooldown. The server persists the cooldown expiry and sends it to the client; ordinary login is accepted only after that expiry. If the report/response is lost, the client stays locally suspended and retries. An active session also reaches the normal acknowledgment timeout. No active-session snapshot-repair endpoint is needed.

Under the single database writer, commit the Kist suspension expiry, invalidated session, login requirement, active-set and checkpoint-participant removal, completion of pending deposits, and returns of all that player's unacknowledged withdrawals together. Finish or definitively reject previously admitted deposits in writer order before settlement closes the session; never admit later old-session traffic. Resolve every accepted item transaction in favor of the Kist. Settled deposits do not require future character removal and cannot block login after the 30-second ban. Append compensating entries with returned stacks, canceled status, next sequence/checksum, and references to original operations. Do not compensate other players' operations because this client missed their entries. Whichever database transaction commits first, acknowledgment or suspension, determines whether a delivery is returned. A late old-session acknowledgment cannot undo a return. Original entries remain unchanged. Database failure leaves pending records recoverable and Kist access disabled until cleanup succeeds.

Return capacity is unlimited. Merge compatible stacks up to normal stack limits, then store overflow stacks with stable IDs and no normal grid slot. Each changed stack has its own compensation entry; session settlement can commit those entries atomically and marks the original operation returned only once. Include overflow in snapshots, checksums, UI, stock queries, crafting, and takes. Normal deposits cannot create overflow. Display actual occupancy above 100%; move overflow into free slots through journaled changes. Fixed-size Unity inventories must not silently drop extra records. Retain the original vault's records after disband for outstanding returns rather than moving items into another hird.

Suspension/cancellation notifications are best effort; server request handlers enforce the ban even if the client ignores the notification. Reject mutations and old-session acknowledgments, and stop sending award payloads for that session. Acknowledge-group removal does not pretend its entries were processed. Do not delete already delivered character items. Returning an award whose receipt was lost can duplicate items; this is allowed. The ban cannot stop a modified client from changing its local inventory or lying about processing; checksums and acknowledgments provide recovery, not cheat prevention.

Store the ban by authenticated player identity, not display name or a client-supplied peer ID. Every Kist request checks the ban and session status, including crafting/station integration. Reconnecting does not clear the expiry. Reject Kist login during the 30-second cooldown. Once it expires, use the same login handler as a regular client: atomically issue a new Kist session UUID, append Login L, and register checkpoint protection at captured C; send the snapshot and journal, then activate the same participant and enable requests after verified catch-up through L. No separate unban/resume protocol is needed. Login timeout leaves access disabled. Apply the same Kist-only restriction to a listen host's local character. Do not call Valheim kick/disconnect APIs or write its server ban list.

Let checkpoint sequence be C and A be the minimum position among active, logging-in, and logging-out checkpoint participants. A new login initially holds C; subsequent positions represent consecutive verified processing. Logout retains its position until acknowledgment through its Logout marker O, when final acknowledgment, session closure, and participant removal commit atomically. Logout rejects new mutations after its marker, requires no processing after O, and has a 30-second completion deadline from marker commit without extending any earlier outstanding acknowledgment deadline. Retries return the same marker/status without extending the deadline; timeout or disconnect uses exclusion and pending-withdrawal cleanup. Apply journal entries C+1 through A to checkpoint state, verify the checksum at A, update checkpoint sequence to A, and truncate the covered log prefix in one SQLite transaction. Leave current state at H unchanged. Temporarily retain records required by a transfer in progress. Keep request deduplication, settled deposit results, and operation-cancellation records independently of truncation. With no checkpoint participants, checkpoint current state after excluded clients' pending withdrawals have been returned. A logging-in session still protects its baseline even when there are no active clients. Disconnect or hird departure removes a session only with pending-delivery cleanup and a new-login requirement; a normal disconnect need not add a timed suspension. Server restart invalidates old sessions and processes outstanding returns before admitting clients. Remaining clients acknowledge return entries before those entries become checkpointable. SQLite WAL checkpoints remain independent of this application rule.

During the 30-second suspension, settle the player's accepted transactions on the server in favor of the Kist: finish pending deposits and compensate unacknowledged withdrawals. Deposits normally keep the reserved item locally until the depositor verifies the committed Deposit entry, removes its exact per-item quantity, and acknowledges it. Uncertain responses retry the same in-memory request identity while the session is valid. On exclusion, retain the committed deposit credit and mark the old character-removal effect settled; never replay that removal into a new session or require reconciliation before enabling access. Lost client state and unsaved character changes can duplicate stock under the accepted character-persistence exceptions. Normal logout drains effects through O; disconnect and failed logout use the same server settlement. There is no client storage or indefinite deposit gate.

Crafting, building, upgrades, stations, and paid-anchor material costs follow the same single-stack withdrawal rules as ordinary takes. An action requiring several stacks submits separate item transactions. Journal each material debit and its consuming recipient, acknowledge completed item effects, and compensate unacknowledged material withdrawals on exclusion. Already produced game effects remain in place, just as already delivered character items remain in place; any resulting duplicate value is covered by the same accepted compensation policy. Existing crafting can also produce its effect before the server rejects or reduces material consumption. Preserving Kist stock in that case is an accepted error in favor of the Kist, including rejection due to admission depth; authorization before the game effect is not required by this plan. No separate crafting recovery protocol is introduced.

## Checksums, snapshots, and replay

Define a canonical item encoding including IDs, slots or overflow status, prefab, quantity, quality, variant, durability, crafter/world-level data, and sorted custom data. Audit every persisted field against actual assemblies. Preserve raw unknown-prefab records. Specify byte widths, encoding, float representation, ordinal sorting, and schema version. Hash all replicated stock, including overflow and any reservations, independent of display order. Compare only equal vault/epoch/sequence/schema. Benchmark full hashing before choosing a Merkle tree; a fixed-slot tree needs an additional overflow hash.

On checkpoint or journal checksum failure, discard the failed temporary update and stop journal processing and Kist requests locally. Do not apply the failed item delivery or acknowledge that entry. Request self-suspension, wait for the server's 30-second cooldown, and perform ordinary login. The failed session is never repaired in place. Ordinary login atomically captures checkpoint state at C, epoch/schema, and per-item settlement statuses, appends Login L, and registers checkpoint protection at C. Retain that snapshot and all entries after C until verified acknowledgments advance the participant or cleanup removes it. Verify the checkpoint and replay through L before activating the session; entries after L follow in order without a retention gap. Completed deposits from excluded sessions require no character removal or reconciliation on login, including when their entries are already checkpointed. Any mismatch during login repeats self-suspension.

Keep replica sequence and in-memory applied character-effect IDs separate, covering each individual award and deposit removal. During a healthy session, repeated inventory entries at or below the verified sequence need only another acknowledgment. Ordinary login installs checkpoint C, resetting replica progress to C, and replays every inventory delta after it. Preserve known applied character-effect IDs while the game process remains running, but do not depend on them across restart. Server settlement status suppresses returned awards and old deposit removals after exclusion; their inventory deltas still replay. Acknowledge each verified replayed entry, including entries whose character award is skipped. Cumulative acknowledgments may encode this consecutive progress without one packet per entry.

Login includes current per-item settlement statuses, including completed deposits whose old character removals must be skipped. Replay the Kist delta of a canceled withdrawal, suppress its character award, and later apply the compensating return delta. Do not skip the entire withdrawal entry: its checksum and intermediate stock must still match. The server's session check rejects messages from the suspended session. Stale in-flight awards may still duplicate stock as already accepted. Outstanding awards must not be removed by checkpoint pruning; only requester acknowledgment or committed cancellation permits that.

Verify login snapshot sequence/checksum before installing, bound chunks/bytes and concurrent logins, and replay subsequent entries. Repeated verification failure repeats self-ban and cooldown; it never enables access to unverified state. Rate-limit reports/login attempts and apply backpressure on journal growth rather than deleting entries above the checkpoint-participant cutoff. Pruning must preserve outstanding awards, deduplication/settlement records, and suffixes temporarily held for login. The 10-second no-op entries detect a lost final update without requiring inventory activity; no separate heartbeat protocol is needed.

## Test plan

Use the milestones in the [main plan](../PLAN-NETWORK-JOURNAL.md#modules-and-milestones) as completion gates. Keep the production state-sync library independent of Unity; the mod adapts it to game objects. Run the same library code in automated tests and in the mod. A modern test runner may host tests, but the production target and SQLite dependencies must remain compatible with Valheim's runtime.

### Module 1: state-sync library

Inject clock, transport, and persistence interfaces. Use plain immutable item records and explicit client inventory results. The test scheduler controls request arrival, message delivery, clock advancement, and failures, so tests do not depend on real sleeps or networking.

| Test layer | Method | Required result |
| --- | --- | --- |
| Deterministic scenarios | Small server/client setups with explicit event order and fake time | Known inputs produce the expected states, journal, acknowledgments, awards, bans, and returns. |
| Model-based simulation | Compare the production code after every event with a small independently written reference model; enumerate short schedules and generate longer seeded schedules | State/sequence/status invariants hold under injected failures. Retain seed and event trace; reduce failing traces to a small regression case. Do not reuse production mutation/replay code as the model's oracle. |
| SQLite integration | Real provider and temporary file-backed databases, including migrations, failed writes, and separate connections where needed | Item changes, journal, results, cancellation, and checkpoints are atomic. Test production schema/configuration rather than an in-memory persistence substitute. |
| Process crash recovery | Run a child server process; terminate it before/after commits, after commit before send, during ban/return, and during checkpoint advancement; reopen the same database | Recovery matches complete committed transactions. Unknown outcomes remain queryable by request ID; no repeated debit or return. A graceful shutdown test is not a substitute for process termination. |

Assert after each state transition:

- Current state equals replay of checkpoint state plus retained replication log, including overflow. Checkpoint advancement does not change current stock.
- Sequences are ordered within a vault/epoch and every entry's checksum describes its resulting state. No-ops advance sequence without changing content.
- A deposit credits once, leaves the reserved character item present until its verified journal entry, and removes it once while its applied identity is known. No cumulative acknowledgment skips a required local removal.
- A request debits once; a cancellation returns once; acknowledged awards are not canceled. Ack/ban races have one serialized outcome.
- Checkpoint advancement never passes a participant's position, including a logging-in session's initial retention floor C and a logging-out session's last acknowledgment. Login registration and logout completion are atomic with their lifecycle transitions. Exclusion removes that session without pretending it processed entries.
- A suspension cancels all that client's pending withdrawals, preserves others' operations, rejects old-session traffic, and requires ordinary login after cooldown.
- Failed verification awards nothing, acknowledges nothing, and immediately requests self-ban. Server suspension returns every pending withdrawal and removes checkpoint participation. After cooldown, ordinary login replays required inventory deltas and suppresses applied/canceled character awards; duplicate entries still receive acknowledgments.
- Given restored communication, successful storage, and enough character capacity, a healthy client eventually reaches the server head. Resync cannot leave it permanently blocked by a canceled award.

Test timers immediately before, at, and after 10 and 30 seconds. Test no-op generation during busy/idle periods, no deadline extension by later traffic, and approximately 40-second worst-case idle-client detection. Test immediate self-ban on journal/checkpoint/no-op mismatch, lost and duplicate self-ban reports, no return duplication or cooldown extension, ordinary login after cooldown, and repeated mismatch during login. Exercise multiple pending withdrawals, login snapshots racing checkpoint pruning/returns, login with no active clients, entries after Login L being checkpointed by other clients, logout racing new commands/checkpoints, lost/duplicate login/logout requests and completion replies, logout timeout/disconnect, full-Kist overflow, disconnect, epoch change, and restart. Vary item field ordering/culture and verify expected checksum equality/differences. Unknown prefabs remain represented rather than disappearing.

Deposit tests cover explicit rejection, missing request/entry/acknowledgment, duplicate replay, blocked local spending, failed/partial removal, disconnect after credit before removal, checkpointed settled deposits on rejoin, and restart before/after local removal. Verify that no timeout refunds an item still present locally and no disconnect automatically reverses a committed credit. Suspension must finish accepted deposits on the server and permit ordinary login after 30 seconds without client storage or a reconciliation gate. Never remove replacement items or replay settled removals from a closed session.

Accounting tests distinguish normal operation from explicitly accepted faults: normal transfers preserve quantities; client crash after acknowledgment can lose unsaved character items; ambiguous receipt/cancellation or restart can duplicate awards. Assert the expected result at each specific crash point rather than claiming global exactly-once delivery or universal item conservation. Those exceptions never permit a repeated server debit or compensating return.

### Performance and release evidence

The goal is an architecture that enables performance through delta replication, asynchronous execution, and bounded work. Numeric performance gates and optimization choices remain open until measurements justify them. Request-result, tombstone, and settlement retention policies also remain implementation decisions; whatever policy is chosen must prevent forgotten retries from executing again and preserve settlement needed for replay.

Measure bytes, encode/decode, UI work, stock queries, allocations, queue length, commit latency, and p50/p95/p99 frame/request latency. Test empty, 32-, 512-, 2,048-stack and overflow vaults with 1/4/10 members, open/closed UI, dedicated servers, and listen hosts. Check build, Harmony targets/access, and category rules against supported assemblies.

Inject duplicates, missed acknowledgments, disconnected observers, full character inventories, ack/suspension races, delayed notifications, blocked award processing, restart during exclusion, and overflow returns. Verify a non-requesting laggard is excluded without reversing another player's take, all of its pending awards return once, and the game connection stays open. Test the 30-second Kist-only ban, login bypass attempts, old-session messages, ordinary login after cooldown, minimum-ack checkpoints, and no-active-client checkpoints. Verify current state equals checkpoint plus journal before/after checkpoint advancement and restart. A checksum mismatch must use self-ban and ordinary login, with no in-place repair. Test login replay without repeated known character awards, repeated acknowledgments, and canceled withdrawals followed by returns. Client save loss and ambiguous extra credit remain accepted.

Initial crash guarantees cover process termination with storage honoring flushes. Verify power-loss behavior on supported filesystems before extending the guarantee. Disk loss and older-backup restoration require separate recovery. Migration preserves the original save. This design has not been runtime tested.

For no-ops, test 10-second generation during idle and busy periods, increasing sequence with unchanged checksum, normal cumulative acknowledgment, missing final-update recovery, and checksum mismatch on a no-op. Drop a client's acknowledgments immediately after a tick and verify suspension roughly 40 seconds later without deadline extension by subsequent no-ops. Verify no catch-up burst of timer entries after restart and no generation for vaults without active clients.


Additional release assertions: distinct concurrent login requests cannot create multiple sessions for one player/vault; old UUID traffic cannot affect a replacement session. At maximum transaction depth, new mutations receive only transient admission errors, stock and sequence remain unchanged by those rejected requests, and existing-result retries, acknowledgments, heartbeats, and settlement still progress. Verify that committed item transactions retain slots until persisted processing acknowledgment or settlement; definitive rejection/failure releases slots, observer acknowledgments do not retain completed slots, and duplicate acknowledgments/settlement cannot release a slot twice. Test asynchronous 100 ms backoff immediately before and at expiry, repeated overload, recovery of pending depth across restart, and once-only acceptance after retry. Reject multi-stack item transactions; multi-stack actions use separately identified single-stack transactions and never repeat completed effects during replay. Verify deposits settle during suspension and ordinary login resumes after the 30-second ban without persistent client state. Exercise crafting and station withdrawals under the same fault/timeout/compensation schedules as takes, including accepted game effects when material consumption is rejected or reduced. Trace game-thread work during bursts, catch-up, checkpointing, and stalled-client traffic: verify no synchronous cross-client waits or unbounded update-loop drains, and report measured latency and observed stutter before choosing numeric performance targets or further optimizations.
